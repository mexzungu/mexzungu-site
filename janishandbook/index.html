Core rules

Three rules that change everything

These are not general tips. They are the difference between burning your budget in two messages and getting ten productive tasks done.

One thing at a time

One topic per message. Not five. When you send five questions at once, Janis has to handle all five in one pass and the answers suffer. Send one, get a sharp answer, then continue.

Be specific

Not: "fix the website."

Say: "The registration button on the Experiences page is broken on mobile. It shows a blank form when tapped."

Vague requests produce vague results.

Share links, not text

Pasting 500 words costs 3x more tokens than sharing a Google Doc link. Janis can read the doc directly. Share the link, save the budget.

Examples

Bad request vs good request

Same goal. Completely different results. And completely different token cost.

Bad

"fix the website."

Which website? Which part? What is broken? Janis has to guess or ask back, burning more tokens either way.

Good

"The registration button on the Experiences page is not working on mobile. It shows a blank form when tapped."

Exact page. Exact element. Exact device. Exact symptom. Janis can act immediately.

Bad

"here is all the text from our brochure [500 words pasted]. Can you summarize?"

500 words pasted is roughly 650 tokens of raw text before Janis even starts thinking. Fully avoidable cost.

Good

"Here is our brochure: [Google Doc link]. Can you summarize it in 3 bullet points?"

Link instead of paste. Janis reads it directly. You specify the format. Zero wasted tokens.

Bad

"do all of this: update the about section, add a new event, fix the footer, and change the color of the header."

Four tasks at once. Any error on one bleeds into the others. Hard to review, hard to course-correct.

Good

"One thing: update the About section to say we are now running events in Barcelona."

Single task. Clear scope. Janis does it, you review it, then you move to the next one. Faster overall.

Bad

"that was not what I wanted, try again."

"Try again" gives Janis nothing to work with. The next version will likely miss in the same direction.

Good

"The tone was too formal. Can you rewrite it to sound warmer and more personal, like you are talking to a friend?"

You name what was wrong and what you want instead. One correction, one better version.

Document workflow

For complex tasks, write it down first

If a task needs 3 or more back-and-forth messages to clarify, it should be a document, not a chat.

How it works

Write your full instructions in a Google Doc. Include all the details: what you want, what to change, what the outcome looks like. Then share the link and say: "Read this and implement what is there."

1 Write spec doc
→
2 Share the link
→
3 "Read this and implement"
→
4 Done
5 clarifying messages back-and-forth ~27,500 tokens
One message with a document link ~3,000 tokens

The document also survives session resets and gives Janis a stable reference if the task continues later.

Use a doc when

  • Major website changes
  • Complex event setups
  • Multi-step processes
  • Anything needing more than 2 clarifications

Skip the doc when

  • Simple questions
  • Quick one-shot fixes
  • You can explain it in 2 sentences
  • The task takes under a minute

Quick tips

Common questions, quick answers

Tap any question to expand it.

How do I tell Janis what format I want?

Just say it at the end of your request. The most useful formats:

  • A numbered list for steps or options
  • A draft email for anything going to a person
  • 3 bullet points for summaries
  • A table for comparisons or structured data
  • A short paragraph for explanations

If you do not specify a format, Janis will pick one. Specifying it means you skip a round-trip correction.

What do I do when a task times out or fails?

Do not retry the exact same message. That uses the same tokens for the same failure. Instead:

  • Break the task into a smaller first step
  • Remove any large pastes and replace with links
  • Start a fresh message with only the core request
  • For code or build tasks: send it as a code task via the API instead of chat
How do I give useful feedback instead of saying "try again"?

Name exactly what was wrong, then say what you want instead. The formula:

  • "The tone was too [X]" tells Janis what register to aim for
  • "It missed the point about [Y]" identifies the specific gap
  • "The format was wrong. I wanted [Z]." specifies the structure
  • "Too long / too short" gives a word count or structure target

The more precise the feedback, the fewer iterations you need.

When should I start a fresh message vs continue the thread?

Start a fresh message when:

  • You are switching to a completely different topic
  • The current thread has gone more than 5 exchanges
  • Janis seems confused by earlier context
  • You want a clean slate without prior assumptions

Continue the thread when the new message directly builds on what Janis just did: corrections, refinements, follow-up steps on the same task.

How do I request research without burning the budget?

Research scales with scope. A few techniques to keep it lean:

  • Narrow the scope before asking. "3 kink educators in Spain" costs less than "research the kink education market."
  • Ask for a summary first. Get 3 bullet points, then drill into the one that matters.
  • Specify the output format. A table with 5 rows costs less than an open-ended deep dive.
  • Set a limit. "Find 3 examples, not 10" keeps the response tight.
