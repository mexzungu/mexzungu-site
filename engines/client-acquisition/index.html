Client Acquisition Engine

The Client Acquisition Engine is how Mexzungu Group finds, qualifies, and closes every new client. It runs autonomously at 07:00 CET every morning, scanning email and WhatsApp for signals, advancing every live lead on cadence, and queuing every Showtime decision for Pepe. No opportunity falls through. No follow-up depends on anyone remembering.

What follows is the complete specification: every trigger, actor, tool call, gate, and failure mode, from the first piece of content published to the signed engagement letter.

Lead Intake. How a Lead Enters the Pipeline

Four entry points create leads in pipeline.json. In all cases, JANIS never auto-creates a lead from an unknown signal. Every new lead requires a deliberate triggering action.

JOANPEPE

Signal Queue Classification

JANIS surfaces unknown inbound to bd-signal-queue.md. JOAN briefs PEPE. Pepe reviews and classifies. On approval, JANIS calls track_lead. Status: new or qualified depending on depth of review.
JANIS

Deal Review Output

When Pepe runs a deal review for someone in his network, the subject is enrolled directly as a qualified lead. Status is set to qualified, not new. Live example: Olivia + Vaman (lead #18).
PEPE

Direct Instruction

Pepe names a lead directly in Telegram or terminal. JANIS calls track_lead with the provided details. Minimum required fields must be present or the call is rejected.
JOAN

Content Inbound

Audience member engages with published content (newsletter reply, LinkedIn DM, website inquiry). JOAN routes to signal queue. PEPE classifies. JANIS enrolls on approval.

track_lead Tool Call. Minimum Required Fields

track_lead(
  name="Company or person name",     // required
  source="signal_queue | deal_review | direct | content_inbound", // required
  track="client | collab",          // required
  status="new | qualified",         // required. deal_review defaults to qualified
  contacts=[{"name": "...", "email": "..."}],  // at least one contact required
  next_action="draft first outreach",    // required
  next_action_date="YYYY-MM-DD",    // required. defaults to today+3 for new, today for qualified
  notes="Source context. How they arrived."  // optional but strongly recommended
)

Fault Recovery and Won Handoff

Fault Classification

WARNING

Log and Continue

Non-blocking. Logged to STATE.md last_error. Run continues. No alert. Examples: empty email scan, WA degraded streak 1-7, missing contact file.

RETRY

3x with 2s Backoff

Transient failures. Tool called up to 3 times with 2-second wait between attempts. Escalates to ERROR on 3rd fail. Examples: Gmail API timeout, WA send failure.

ERROR

Skip Step. Continue Run.

Step is skipped. Run continues. Logged to STATE.md. iteration_count NOT advanced. Included in Telegram summary. Examples: auth token expired, email send failure after 3 retries.

CRITICAL

Abort Run. Ticket to LARS.

Run aborts immediately. Does not advance iteration_count. Creates LARS ticket. Examples: pipeline.json missing on load, pipeline.json write failure on Step 10.

flowchart TD A([Step fails]) --> B{Retry eligible?} B -->|Yes| C[Wait 2s. Retry.] C --> D{Attempt 3 reached?} D -->|No, still failing| C D -->|Yes, still failing| E[Escalate to ERROR] B -->|No, not retryable| E E --> F{Is this pipeline.json?} F -->|Yes| G[CRITICAL. Abort. Ticket to LARS.] F -->|No| H[Log to STATE.md. Add to failed_items.] H --> I[Skip step. Continue run.] I --> J{Failed 3 consecutive runs?} J -->|Yes| K[Circuit breaker: permanent failed_items] K --> L[Skip permanently until manual clear] J -->|No| M[Retry eligible next run]

Circuit Breaker

A step that fails 3 consecutive runs is added to failed_items in STATE.md and skipped permanently until BOWIE or LARS manually removes the entry and clears the failure count. The overall run continues past the circuit-broken step.
