AI Agent Building Engine

The AI Agent Building Engine is how Mexzungu Group designs, builds, tests, deploys, and maintains autonomous AI agent systems for clients. From a client brief to a running cron job in production. Every engagement follows the same 8-phase build journey: requirements locked, architecture approved, code reviewed, coverage gated, then live.

What follows is the complete specification: every phase, actor, tool call, coverage gate, and failure mode, from first client brief to a monitored production deployment.

Intake Triggers

What starts a build engagement. Three trigger paths. All require EL before any build work begins.

Path A. Inbound Direct

Client requests AI agent system

Client contacts Pepe directly via WhatsApp, email, or referral. JAGGER qualifies within 48 hours. If fit confirmed, PEPE approves first contact and brief session is scheduled.

Gate: Showtime First contact. Showtime EL send.

Path B. From Delivery Arms

Existing client requests agent build

Active client in Founders or Investors arm identifies automation need during engagement. LARS captures scope expansion. JAGGER prices the add-on. New EL or amendment required before build.

Gate: Soundcheck Scope capture. Showtime EL amendment.

Path C. MGL Induction Pipeline

Induction graduate refers build engagement

Consultant completing MGL Induction identifies a client opportunity requiring agent build capability. JAGGER evaluates for co-delivery or solo engagement. PEPE approves commercial structure.

Gate: Showtime Co-delivery terms. Showtime EL.

Hard Block

EL must be signed before any build work

No code is written, no architecture is designed, and no stack audit is performed until an engagement letter is countersigned by both parties. Scoping conversations are pre-EL. Build work is not.

Enforced by LEMMY contract check at Phase 0 exit.

Build Cycle

The six-step sequence BOWIE's team runs for every active engagement sprint (weekly or bi-weekly). Tool calls listed for each step.

STEP 1 Sprint kick-off and task queue review

BOWIE opens the sprint by reviewing the project STATE.md, all open code tasks, and any items that failed in the previous cycle. LARS updates the ticket board and sets sprint goals.

Tool calls

read_brain(path="brain/loops/[client-build]/STATE.md")
ticket_list(project="[client-build]", status="open")
read_brain(path="brain/loops/[client-build]/failed_items.md")
ConditionSeverityAction
STATE.md has failed_items from last sprintErrorRetry failed items before adding new scope
No STATE.md found for this projectCriticalInitialize STATE.md immediately, halt sprint until done
STEP 2 Code task dispatch

BOWIE spawns code tasks for all sprint work items. Each task is scoped to 8 minutes maximum. Tasks over 8 minutes are split before dispatch. Every spawned task is registered with /code-task/watch.

Tool calls

run_task(endpoint="/code-task", task="[task spec]", model="sonnet", commit=true)
run_task(endpoint="/code-task/watch", task_id="[task_id]")
ConditionSeverityAction
Task estimated over 8 minWarningSplit task before dispatch. Two smaller tasks over one large one.
Task fails 3 consecutive timesErrorEscalate to BOWIE with root cause. Do not retry without a diagnosis.
Task dispatched without /code-task/watch registrationCriticalRegister immediately. Fire-and-forget is banned across this engine.
STEP 3 Connector health and API validation

NILE checks all API connectors used by the build. Validates OAuth tokens, confirms rate limits are not approaching, runs smoke tests against live endpoints. Flags any degradation to BOWIE before the next code task is dispatched.

Tool calls

read_brain(path="brain/memory/connector-health.json")
run_task(cmd="curl -s http://127.0.0.1:8741/health | head -c 200")
run_task(cmd="python3 janis/tests/test_[connector].py")
ConditionSeverityAction
OAuth token expiredErrorTrigger token refresh immediately. Halt tasks using that connector.
API endpoint returns non-200WarningLog to connector-health.json. Retry in 30 min. Escalate if 3x.
Rate limit at 80%+ of quotaWarningAlert NILE. Throttle automated calls. Notify client if user-facing.
STEP 4 Coverage check and test run

LOU runs the full test suite and coverage report on all sprint deliverables. JACK validates integration test results against live APIs. Coverage regression below sprint baseline blocks the next code task dispatch.

Tool calls

run_task(cmd="python3 -m coverage run -m pytest brain/janis/tests/ && python3 -m coverage report")
run_task(cmd="bash brain/janis/tests/run_tests.sh")
ConditionSeverityAction
Coverage drops below 80%CriticalBlock all new code task dispatch until coverage is restored
Integration test fails on previously passing toolErrorRoot cause in same turn. Do not advance sprint until resolved.
SyntaxWarning or regex escape bug in test outputWarningFix before calling sprint done. No warnings in production output.
STEP 5 Git commit and service restart

Every sprint deliverable is committed to git before the session closes. If the sprint modified tools_server.py or any dashboard file, the service is restarted and health check confirmed. No uncommitted changes left in working tree.

Tool calls

run_task(cmd="git add [files] && git commit -m '[commit message]'")
run_task(cmd="systemctl --user restart janis-tools && sleep 5 && curl -s http://127.0.0.1:8741/health | head -c 100")
ConditionSeverityAction
Uncommitted changes at sprint closeCriticalCommit before session handoff. Data loss is non-negotiable to prevent.
Health check returns non-200 after restartErrorDiagnose immediately. Sprint is not done until service is live.
STEP 6 Client progress update

LARS sends the client a one-paragraph sprint update: what was completed, what is next, whether any questions or decisions are needed. No more than 5 days between updates on any active build. WhatsApp by default, email only if client prefers.

Tool calls

send_whatsapp(to="[client number]", message="[sprint update]")
write_brain(path="brain/loops/[client-build]/STATE.md", content="[updated state with sprint summary]")
ConditionSeverityAction
5 days without a client update on active buildErrorSend update immediately, regardless of sprint status or blocker
Client question requires PEPE inputWarningRoute to PEPE via Telegram same day. Do not leave unanswered over 24h.

Fault Reference

Documented failure modes across the build lifecycle. Each has a severity, owner, and recovery path.

FaultSeverityOwnerRecovery
Requirements change after architecture lock Critical PEPE Stop build. Re-run Discovery phase. New PEPE gate required before resuming. Timeline and commercial terms reviewed.
Coverage drops below 80% mid-build Critical LOU Block all new code task dispatch. LOU identifies uncovered branches. Restore coverage before next sprint starts.
Code task fails 3+ times on same item Error BOWIE BOWIE reviews root cause in same turn. Do not re-dispatch until root cause is understood. Escalate to PEPE if architectural blocker.
OAuth token expired, blocking integration build Error NILE NILE triggers token refresh immediately. Audit all other connectors in same session for expiry risk. Update refresh schedule.
Client requests scope change mid-build Warning LARS LARS captures request. BOWIE assesses impact on architecture. Material scope change requires PEPE-approved EL amendment before new build work starts.
Tools server down during active build session Error BOWIE Restart janis-tools immediately. If restart fails, diagnose before continuing. No code tasks dispatched while server is down.
Client VPS incompatible with planned architecture Critical BOWIE Halt build. Re-run stack audit. Redesign architecture for client infra. PEPE approves revised blueprint. Commercial terms reviewed with JAGGER.
OpenAI quota exhausted during build Warning IGGY Switch to Gemini immediately. Never retry OpenAI. Update agent config in same turn to use Gemini endpoint.

Standing Rules

Behavioral rules that apply to every build engagement. Not subject to client request or timeline pressure.

  • EL before any build workNo architecture, no code, no stack audit until the engagement letter is countersigned by both parties. LEMMY enforces at Phase 0 exit.
  • Architecture approval is a hard gatePEPE must explicitly approve the blueprint before any code task is dispatched. No implicit approvals and no "proceed unless you hear back."
  • Code tasks max 8 minutesAnything estimated over 8 minutes is split before dispatch. Large tasks create unmonitorable failure surfaces.
  • All tasks registered with /code-task/watchFire-and-forget is banned. Every dispatched task has a watchdog registration. IGGY enforces this without exception.
  • 80% coverage gate, no waiversCoverage below 80% blocks deployment. If timeline pressure arrives, scope is cut, not coverage.
  • All tools registered in health endpoint before handoverA tool not in the /health endpoint does not exist. Tools claimed done but not registered are not done.
  • Auto-commit every change to gitEvery sprint deliverable is committed before the session closes. Merge conflicts resolved before push. No data loss.
  • Switch to Gemini when OpenAI quota is exhaustedNever retry OpenAI after hitting quota. Update agent config in the same turn. Permanent standing rule.
  • Client updates every 5 daysNo active build goes 5 days without a progress message from LARS. No exceptions, regardless of sprint status.
  • Service restart after tools_server.py changesCommitted but not restarted is not live. Health check must return 200 before the sprint is reported done.
